## 1. 원판 장수 증가로 개별 부재의 길이 초과를 해결할 수 없다

HTML 394행은 네스팅 확장 완료 조건을 “S4 — 거부 대신 2장 배치”로 적었다.
S4는 외곽 900×1500이며 고정틀 세로재 `F01-1` 자체가 1500×40 mm다.
같은 입력으로 현재 생성기를 실행하면 다음과 같이 거부된다.

```json
{
  "rule": "nesting.part_fits_stock",
  "part_id": "F01-1",
  "part": [1500, 40],
  "usable": [1180, 860]
}
```

1220×900 원판의 장수를 늘려도 1500 mm 단일 부재가 들어갈 판은 생기지 않는다.
따라서 다음 두 경우를 분리해야 한다.

- **개별 부재가 원판을 초과:** 충분히 큰 원판을 선택하거나 명확히 거부한다.
  부재를 나눠 이어 붙이는 방법은 별도의 결합 설계이며 네스팅 기능에 포함하지 않는다.
- **개별 부재는 들어가지만 전체 부품을 한 장에 배치할 수 없음:** 여러 원판으로 배치한다.
  이 조건을 만족하는 별도 입력을 다중 원판 기능의 합격 사례로 만든다.

S4는 현재 원판 규격에서 계속 거부되는 것이 맞다. HTML 374행의
“부품 ≤ 원판 가용 범위 → 다중 원판” 대응도 같은 기준으로 고쳐야 한다.

## 2. 211건 해시 대조는 요청별 프로세스 격리 시험이 아니다

HTML 407행의 “회귀 시험이 이미 이 방식으로 211건을 돌린다”는 설명은 코드와 다르다.

- `RegressionBase.setUp()`은 unittest 메서드마다 임시 폴더를 만든다.
- `DecimalSweep.test_two_hundred_sizes()`는 같은 메서드의 폴더에서 200개 입력을 순서대로 실행한다.
  입력마다 빌더 모듈을 다시 불러오지만 프로세스는 같다.
- `--record`가 띄우는 별도 프로세스는 일반 모드와 최적화 모드 두 개다.
- 211은 각 모드에서 생성한 DXF를 입력별로 대응시켜 해시를 비교한 건수다.

근거: [시험의 작업 폴더와 빌더 로딩](unified/03_tests/test_regressions.py:43),
[소수 반복 시험과 프로세스 실행](unified/03_tests/test_regressions.py:219).
현재 기록은 두 모드 각각 시험 8개, 로그 항목 238개, DXF 해시 대조 211/211 일치다.
시험 기록에 담긴 CNC 소스 해시도 현재 파일과 일치한다. 이번 검토에서 전체 시험을 다시 돌리지는 않았다.

요청마다 작업 폴더와 프로세스를 분리한다는 **구현 권고는 유지**한다.
완료 조건에는 서로 다른 입력의 동시 실행, 한 작업의 실패, 작업 간 파일·파라미터 혼입 방지를 별도로 넣는다.

## 3. 입력 오류의 규칙 ID와 검증기의 표시 이름을 분리해야 한다

HTML 410행은 규칙 ID·검사 이름에 안내 문구를 대응시키면서 “ID가 고정”이라고 설명한다.
`ParameterError.rule_id`에는 해당하지만, 형상 검사 이름에는 입력 수치가 들어간다.

임시 복사본에서 창살을 2+4에서 3+5로 바꿔 64개 검사를 통과시켰다.
이때 이름 8개가 바뀌었다. 예를 들면 다음과 같다.

| 2+4 | 3+5 |
|---|---|
| `total_base_pockets_104` | `total_base_pockets_148` |
| `52_joint_pairs_XY_match_opposite_faces` | `74_joint_pairs_XY_match_opposite_faces` |
| `lattice_2_vertical_4_horizontal_bars_per_leaf` | `lattice_3_vertical_5_horizontal_bars_per_leaf` |

근거: [수치를 포함하는 검사 이름](unified/02_cnc/build_portrait_double_leaf.py:423).

서비스용 결과에는 고정된 `rule_id`, 대상 부품/입력 필드, 기대값, 실측값, 허용 오차,
판정 상태를 각각 둔다. 사용자용 문장은 이 데이터에서 생성한다.
검사 이름을 문자열 패턴으로 해석해 번역표에 연결하는 구조는 피한다.

## 4. 기존 산출물 보존은 CAD 검증 실패까지 보장된다

HTML 409행의 “실패하면 이전 산출물이 그대로 남는다”에는 **저장 전·후 CAD 검증 실패 시**라는 조건이 필요하다.

현재 `build()`는 CAD 검증이 끝나면 spec/DXF를 교체하고 검증 리포트와 CSV를 기록한다.
그 뒤 `main()`이 PNG, README, 최종 매니페스트를 만든다.
근거: [CAD 검증 후 파일 교체](unified/02_cnc/build_portrait_double_leaf.py:349),
[그 뒤의 렌더링 단계](unified/02_cnc/build_portrait_double_leaf.py:1126).

현재 패키지를 임시 폴더로 복사하고, 입력을 3+5로 바꾼 뒤 첫 PNG 렌더 함수에 예외를 주입했다.
CAD 검증 64개가 통과한 다음 빌드가 실패했으며 결과는 다음과 같다.

- spec, DXF, CSV 4종, 검증 리포트는 새 설계로 바뀌었다.
- PNG 5장과 패키지 매니페스트는 이전 값으로 남았다.
- 바꿔 넣은 입력 JSON까지 합하면 기록된 파일 중 8개가 달라졌다.

이는 CAD 검증 실패를 보호하는 R3 조치가 잘못되었다는 뜻이 아니다.
**패키지 전체의 실패 보호는 서비스 계층에서 추가해야 한다**는 뜻이다.
HTML에 이미 있는 “작업 폴더 단위로 합격한 패키지만 공개”를 구체적인 완료 조건으로 승격한다.

1. 새로운 작업 폴더에서 모든 산출물을 생성한다.
2. DXF 검사, 산출물 누락 검사, 최종 매니페스트 대조까지 완료한다.
3. 완료된 패키지만 다운로드 대상으로 공개한다.
4. 검증·CSV·렌더링·최종 기록 단계에 실패를 주입해 이전 공개 패키지가 유지되는지 확인한다.

## 구현 순서에 반영할 내용

첫 구현 범위는 **외곽 크기·창살 수·단문 좌/우 또는 양문 입력으로 패키지를 생성하는 CLI**로 잡을 수 있다.
원판 한 장을 넘는 입력은 명확한 이유로 거부해도 이 첫 범위를 완성할 수 있다.

| 순서 | 변경 | 완료 조건 |
|---|---|---|
| 1 | 회귀 기준 보존, 입력 스키마·기본값·프리셋, 그림 선택 모듈 | 외곽 크기만 바꿔도 나머지 치수가 유도됨. 기존 R3 프리셋의 생산 형상 보존 |
| 2 | 형식 모듈·검증기·도면 문구를 함께 일반화 | 단문 좌/우·양문과 창살 0개 조합의 의도된 결과 확인. 도면·수량·하드웨어 참고 위치 일치 |
| 3 | 고정 오류 ID, 작업별 실행, 패키지 전체 공개 처리 | 서로 다른 입력의 동시 실행 및 실패 주입에서 결과 혼입과 불완전 패키지 공개 없음 |
| 4 | 원판 여러 장 배치와 원판 선택 | 개별 부재 초과와 전체 배치 부족을 구분하고 원판별 파일·수량·배치 정보를 생성 |
| 5 | 필요에 따라 웹 입력 화면 | CLI와 같은 입력 모델·오류·검증 결과를 사용 |

최소 잔존 폭 등 제작용 하한은 시험편 근거가 확보되기 전까지 PENDING으로 유지한다.
수치 정책을 둔 기하 합격을 제작 승인으로 확대하지 않는다.

게시 URL `https://claude.ai/code/artifact/c07ee21e-e77f-40c2-a161-606600dfa23e`는 읽기 도구에서 열리지 않았다.
따라서 게시 화면 자체가 아니라 위 경로의 로컬 HTML에서 “3판 2026-09-12 검토 반영” 표시와 내용을 확인했다.
네 지적의 정정, 개별 부재 초과와 전체 배치 부족의 구분, 고정 검사 ID, 패키지 전체 공개 조건이 반영되어 있다.
첫 구현 범위를 1~4단계로 제한하고 다중 원판을 후속 단계로 둔 순서도 일치한다.

입력별 결과, 프로세스 ID, 실행 시각, 소스 해시는

향후 구현할 CLI의 작업 접수·공개 경로까지 검증한 것은 아니다. 3판에 적힌 실제 작업 경로 재시험 조건을 유지한다.

### 추가 메시지의 “규격·DXF 한 쌍이 원자적”은 정정 필요

3판 HTML은 보장 범위를 CAD 검증 실패로 한정하여 올바르게 설명한다.
다만 함께 전달된 메시지의 “규격과 DXF 한 쌍만 원자적”이라는 문장은 현재 코드와 다르다.

현재 교체 코드는 [빌더 362행](unified/02_cnc/build_portrait_double_leaf.py:362)의
`tmpspec.replace(SPEC); tmp.replace(DXF)`다. 두 번의 파일 교체를 순서대로 실행한다.
Python 문서가 설명하는 원자성은 성공한 개별 `os.replace()` 호출에 적용된다.
두 호출을 묶은 트랜잭션이 되지는 않는다. [Python 공식 문서](https://docs.python.org/3/library/os.html#os.replace)

현재 패키지의 임시 복사본에서 3+5 설계를 만들고, 두 번째 `Path.replace()`에 `OSError(EIO)`를 주입했다.
저장 전·후 CAD 검증 뒤 두 번째 교체에서 예외가 발생했으며 다음 상태가 남았다.

- `design_spec.json`은 새 설계의 부품 28개로 갱신되었다.
- DXF, 검증 리포트, 매니페스트는 이전 설계의 값으로 남았다.
- 새 `_validated_candidate.dxf`가 남았다.

정확한 표현은 **“검증을 모두 통과한 뒤 spec과 DXF를 순차 교체한다”**다.
4단계 완료 조건에 교체 도중 I/O 오류와 프로세스 종료도 포함한다.
완성한 패키지를 별도 버전 폴더에 두고, 다운로드가 참조하는 패키지를 한 번에 전환하는 방식으로 구현할 수 있다.
일반적인 `os.replace()`로 기존의 비어 있지 않은 폴더를 그대로 덮어쓸 수 있다고 전제하지 않는다.
전원 장애 뒤의 영속성까지 보장하려면 별도의 저장 동기화 정책이 필요하며, 이번 시험은 그 보장을 검증하지 않았다.

이 정정은 3판의 구현 순서를 바꾸거나 현재 CNC 소스를 추가로 수정할 이유가 아니다.
패키지 전체 공개 기능을 4단계에 구현한다는 기존 범위에서 함께 처리한다.
새 시험 뒤에도 현재 패키지 28개와 `from_codex` 원본 37개 파일의 해시는 모두 일치했다.
