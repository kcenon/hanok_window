# 출력 형식 등록

`engine/output_formats.py`는 DXF에서 파생하는 결정적 출력의 순서와 파일 이름·쓰기 함수·읽기 검증 함수·검사 ID·보고 위치를 선언합니다. 현재 등록된 출력은 AI입니다. DXF는 기하 모델과 저장 후 재검증의 기준이며, DWG는 기존처럼 내려받을 때만 변환합니다.

이 작업은 [#34](https://github.com/kcenon/hanok_window/issues/34)의 후보 2입니다. PNG·CSV·README 쓰기 함수를 별도 모듈로 옮기는 후보 1, 전체 검사 이름을 상수로 바꾸는 후보 3, 부재 종류·기하 계산의 분리는 후속 범위입니다.

## 새 출력을 추가할 때

1. `engine/`에 구현 모듈을 둡니다. `write(cfg, doc, path)`는 전달받은 경로에 후보 파일을 쓰고, `verify(doc, path)`는 그 파일을 읽어 현재 DXF와 대조한 `(통과 여부, 실측값)`을 돌려줍니다. 검증 함수는 도면과 파일을 바꾸지 않습니다.
2. `output_formats.py`에 구현을 함수 안에서 불러오는 쓰기·검증 연결 함수와 `OutputFormat` 항목을 추가하고 `FORMATS`에 순서대로 넣습니다. 파일 이름과 검사 ID는 중복 없이 정합니다. 기본 출력 경로는 `cfg.OUT / filename`입니다. 기존 AI의 `path_attribute="AI"`는 이전 호출자의 `Design.AI` 경로 변경을 보존하며, 새 형식에는 설계 필드를 추가할 필요가 없습니다.
3. 출력 자체의 결정성·읽기 검증·오류 시험과 사용자 안내를 추가합니다. 웹에서 새 확장자의 MIME 처리가 필요하면 그 표도 별도로 갱신합니다.

등록 모듈은 표준 라이브러리만 불러옵니다. 쓰기·검증 연결 함수의 지연 import를 유지해야 웹·LLM 프로세스가 메타데이터를 읽으면서 `builder`·`ezdxf`를 불러오지 않습니다. 사용자 설정으로 모듈을 탐색하거나 외부 플러그인을 실행하는 구조는 없습니다.

| 연결 위치 | 등록 정보의 사용처 |
|---|---|
| `builder.build()` | 후보 쓰기·정리·검증 후 파일 교체 |
| `builder.validate()` | 파일 이름을 키로 한 `export_paths`와 등록된 검증 함수 순회 |
| `validation_rules.RULE_IDS` | 기존 AI 검사 위치에 등록된 출력 검사 ID를 순서대로 삽입 |
| `package.required_files()` | 공통 필수 파일과 등록된 출력 파일의 합집합 |
| 생성되는 `README.txt` | DXF 다음에 등록된 출력 파일 이름을 순서대로 표시 |

따라서 출력 구현과 등록을 두 파일에서 추가하면 위 다섯 연결 위치는 그대로 사용합니다. 새 형식별 `validate()` 인자나 검사 호출을 더하지 않습니다. 기존 `ai_path` 위치·키워드 인자는 계속 지원하며, 함께 지정한 경우 같은 AI 항목의 `export_paths`보다 우선합니다. 기존의 명세 파일 없는 독립 검증도 유지합니다.

## 검증과 게시 순서

출력 후보를 먼저 쓰고 메모리의 DXF와 대조한 뒤, DXF를 저장해 다시 읽고 같은 후보를 재검증합니다. 현재 AI 검사는 두 단계 모두 `ai_export_matches_saved_dxf`이며, 완성 패키지의 검사 71개와 순서는 같습니다. 두 단계가 통과하면 명세·DXF·출력을 차례로 교체하고 검증 기록과 CSV를 씁니다.

오류가 나면 명세·DXF·모든 출력 후보를 정리합니다. 검증 실패는 기존 파일을 교체하지 않습니다. 직접 `builder.build()`를 부를 때 여러 파일의 교체 전체가 원자적인 것은 아닙니다. 공개 생성 경로는 작업별 임시 폴더에서 빌드·그림 생성·봉인을 마친 패키지만 게시하므로, 생성 실패가 이전 완성 패키지와 `latest.json`을 바꾸지 않습니다.

`tests/test_output_formats.py`는 실제 생성에서 두 문서의 검증, 기존 경로 인자, 부분 쓰기·누락·잘못된 파일·두 번째 출력 실패·저장 후 거절·읽기 오류를 확인합니다. 실제 작업 프로세스에 시험용 출력을 하나 등록해 후보 작성, 검사 72개, 필수 파일, README 안내와 봉인까지 연결되는지도 확인합니다. 시험용 형식은 제품에 등록하지 않습니다.

## 패키지 ID와 회귀 기준

패키지에는 현재 엔진 소스가 복사되고 `environment.json`에 그 해시가 기록됩니다. 소스를 바꾼 리팩터링 전후의 `package_id`를 같게 유지하면 현재 소스의 출처를 보존할 수 없습니다. #34의 원래 ID 불변 기준은 다음 기준으로 수정합니다.

- 같은 환경에서 변경 전후 예제 5종의 DXF·AI·PNG·CSV·설계 JSON·README·검증 기록 바이트가 같습니다. 검사 수·순서·실측값·설계 리비전도 같습니다.
- 차이는 실제로 바뀐 소스와 추가 소스, `environment.json`의 `source_sha256`, 그 결과인 매니페스트로 한정하고 모두 기록합니다. 해시 알고리즘과 필수 파일 검증은 유지합니다.
- 변경 후 같은 소스·환경의 반복 생성과 포함 소스로 하는 최적화 실행은 전체 파일과 패키지 ID가 같습니다.

`output_formats.py`가 재생성용 소스에 추가되어 파일은 37개에서 38개로 늘었습니다. 매니페스트까지 담은 ZIP은 39개입니다. 예제 기록과 설명서 그림의 과거 패키지는 당시 값으로 남깁니다. 운영체제 간 차이는 기존 CI 비교 기준을 적용하며, 같은 환경에서의 변경 전후 비교와 구분합니다.
